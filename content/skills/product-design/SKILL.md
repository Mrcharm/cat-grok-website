# 产品设计技能

## 1. 适用场景

用于新产品规划、存量产品重构、功能优化、平台改造、AI产品设计、内部管理系统、数据研发工具及多智能体平台等需求。最终主产物必须是标准PRD；当用户提供原文档、Demo、截图或历史版本时，必须采用保留式改造，不得无理由推倒重写。

## 2. 核心目标

1. 将零散需求转化为结构完整、逻辑闭环、可实施和可验收的产品设计。
2. 最大化保留原有正确内容、页面结构、术语、图片和已确认规则。
3. 补齐用户角色、业务流程、功能边界、交互状态、权限、异常、非功能和验收标准。
4. 产出与PRD一一对应的可评审原型设计，关键页面、组件和状态均有编号。
5. 最终交付标准PRD，优先为可编辑DOCX；原型按任务要求输出可编辑PPTX、HTML、Figma说明、图片或嵌入Word。

## 3. 输入

至少读取用户已提供的全部相关材料：原始需求、旧版PRD、会议纪要、Excel、Demo代码、截图/动图、接口约束、业务流程、操作手册、历史确认结论。信息不足但不影响主结构时，使用“待确认”标记继续完成，不重复询问历史中已经明确的信息。

## 4. 强制工作流

### 4.1 建立基线

- 识别当前有效版本、历史版本和废弃版本。
- 提取不可变约束：名称、角色、流程、范围、接口、数据、排版、字体、版本命名。
- 建立“保留 / 修改 / 新增 / 删除 / 待确认”清单。

### 4.2 需求分析

- 明确背景、问题、目标、成功指标、范围和非范围。
- 识别用户角色、核心场景、业务链路、前置条件和结果。
- 对模糊需求进行归一化，区分业务目标、用户需求、功能需求和实现建议。
- 使用“必须 / 应 / 建议”表达强约束、推荐要求和后续增强。

### 4.3 产品结构设计

- 输出产品架构、模块边界、信息架构、页面清单、权限矩阵和目标流程。
- 页面和功能按用户任务组织，不按后端表或接口机械分组。
- 关键业务流程须提供中文流程图或泳道图，并覆盖异常分支。

### 4.4 原型设计

- 先对齐现有Demo、截图、组件库和导航体系，再补强缺失能力。
- 为每个关键页面分配页面编号，为关键组件分配组件编号。
- 原型必须体现：页面结构、字段、按钮、菜单、弹窗、提示、权限和状态。
- 至少覆盖正常、空、加载、成功、失败、无权限、禁用、重复提交和并发冲突等适用状态。
- 原型说明必须写清：使用角色、进入方式、用户动作、系统反馈、保存/校验、异常提示和关联规则。
- 不得用整张截图冒充可编辑原型；基于截图改造时标记保留区、修改区和新增区。
- 中文界面和泳道图必须确保中文可正常显示。

### 4.5 详细功能设计

每个功能模块至少包含：

1. 功能目标和用户价值。
2. 适用角色、入口和前置条件。
3. 业务规则。
4. 用户动作 → 系统反馈 → 保存/校验 → 异常提示。
5. 字段、控件、默认值、必填、格式、数据来源、联动和错误文案。
6. 状态、权限、快捷键、撤销/回退、版本和并发规则。
7. 关联原型编号和验收标准。

### 4.6 数据与系统边界

仅输出评审和实施必要的数据对象、输入输出、接口边界、调用时机、权限和失败策略。除非用户明确要求，不强行生成冗长接口清单，也不得把技术实现细节冒充产品需求。

### 4.7 AI 产品约束（合并自 PRD-SKILL 3.4）

AI 不能作为装饰性章节。凡涉及 AI 能力的功能，必须落到具体链路：

1. 输入与上下文来源；
2. 智能体职责与边界；
3. 工具调用条件与权限；
4. 统一输入输出 Schema；
5. 证据来源、置信度和冲突处理；
6. 人在环确认点；
7. 超时、工具失败、证据不足和降级策略；
8. 审计字段、Prompt/模型/规则版本；
9. 禁止编造表、字段、码值、历史 SQL 和业务规则。

**固定判断、循环、阈值、超时、重试和状态流转应放在编排器/规则引擎，不包装成自由发挥的 Agent。**

### 4.8 产品逻辑闭环十问（合并自 PRD-SKILL 3.2，用于 4.5 的自检）

每个核心功能写完后逐问核对：谁在什么场景下使用 / 从哪里进入 / 前置条件是什么 / 输入什么 / 系统如何处理和判断 / 产生什么中间状态 / 输出什么 / 用户下一步做什么 / 信息不足、超时、失败、无权限、冲突时如何处理 / 如何保存、审计、回退和验收。

禁止只写"支持……""系统自动判断""必要时提示"等不可实现表述。

### 4.9 验收与交付

- 生成需求追踪矩阵：需求 → 页面 → 功能 → 原型 → 验收项。
- 检查术语、编号、目录、图题、页面编号和版本一致。
- DOCX必须使用正式中文字体：正文宋体，标题黑体或宋体加粗。
- 任何DOCX生成或修改后必须渲染检查全部页面；发现溢出、错位、缺图、乱码或表格断裂时必须修复后再交付。

## 5. 标准PRD结构

1. 文档控制与修订记录
2. 引言：背景、问题、目标、范围、术语、引用
3. 用户与业务分析：角色、场景、现状流程、目标流程、泳道图
4. 产品总体设计：架构、模块、信息架构、页面清单、权限、全局规则
5. 原型设计：原型原则、页面原型、组件标注、状态设计
6. 详细功能设计：功能、交互、字段、规则、状态、异常、权限
7. 数据、接口与系统边界
8. 非功能要求：性能、容量、稳定性、安全、兼容、可用性、可观测性
9. 验收、上线、运营与实施计划
10. 附录：需求追踪、待确认、原型索引、测试映射

可根据用户指定模板调整章节编号和名称，但不得遗漏关键内容。

## 6. 输出要求

主输出：`项目名称_产品需求文档_PRD_Vx.x.docx`。

可选配套输出：

- `项目名称_原型设计_Vx.x.pptx/html/png`
- `项目名称_需求追踪矩阵.csv`
- `项目名称_变更说明.md`

## 7. 禁止事项

- 不推倒重写用户要求保留的原文档。
- 不改变已确认术语、角色、智能体或工具名称。
- 不只给泛化产品方案而缺少页面、交互、状态和验收。
- 不把所有新增要求生硬追加到文末。
- 不输出不可编辑截图并声称是可编辑原型。
- 不遗漏异常态、权限和非功能指标。
- 不在未校验排版时交付DOCX。

## 8. 质量门禁

执行 `checklists/PRD交付自检清单.md`（P0 项任一未过不得声明完成）+ `templates/验收清单.md`。任何"核心流程不闭环、关键页面无原型、交互无反馈、角色权限不清、编号不一致、文档排版未验证"的产物均不得判定完成。
