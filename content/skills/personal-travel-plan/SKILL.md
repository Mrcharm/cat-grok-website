# 个性化旅游攻略

## 这个技能解决什么

不是"景点罗列 + 网红打卡清单"，是**可执行、可核验、敢砍**的行程文档：

- 每个数字能落到「谁、几点、多少钱、在哪买」
- 每个"要不要去"有量化结论，敢说不划算
- 天气/票价/末班/放票时间都标来源与抓取日期
- 出一份用户能直接照着走的 DOCX，而不是聊天里的一段话

**方法论与城市无关，只有"必查项"和"节奏参数"随城市变化** —— 换城市走 `references/city-profiles.md` 的类型矩阵，流程不动。

默认开启**适老化模式**（携 65 岁上下长辈）。用户说明是情侣/朋友/独自出行，关掉 2.1 节即可，其余规则照用。

## 一、开工前问完 7 件事（一次问完，不挤牙膏）

| # | 问什么 | 为什么必须问 | 没答时的默认 |
|---|---|---|---|
| 1 | 出发城市 + 交通方式 | 决定 D1 的落地时刻与接驳 | 从航班/高铁时刻库反推最优 |
| 2 | 日期、天数、**返程时刻** | 返程时刻是排程第一锚点，比去程更硬 | 无返程时刻不开工，先问 |
| 3 | 同行人：年龄、体力、忌口、是否午休 | 触发适老化/亲子模式 | 按适老化处理 |
| 4 | 必去 1–3 个（排序）+ 明确能砍的 | 分清"用户想要"和"值得去" | 按目的地核心度排序 |
| 5 | 已订硬约束：机票/酒店/已付款项目 | 这些是不可变项，排程围绕它们 | 视为未订，给两套方案 |
| 6 | 交通偏好 + 单程车程上限 | 决定租车/包车/打车 | 不租车；老人单程 ≤1.5h |
| 7 | 预算口径 | 只算落地待付，还是含机酒 | 默认"落地待付"，机酒已付则单列 |

问完再动手。宁可这一轮多问两个问题，也不要交一份"正确的废话"。

### 1.1 目的地画像（3 分钟，决定后面查什么）

| 维度 | 取值 |
|---|---|
| 城市类型 | 海滨/海岛 · 山水/峡谷 · 古城/古镇 · 都市 · 高原 · 冰雪 · 温泉 · 境外 |
| 景点密度 | 核心区步行圈可串 vs 必须包车跑郊县 |
| 到达枢纽 | 机场/高铁站 → 市区 km / 分钟 / 有无轨道 |
| 核心住宿区 | 景区步行圈 / 商业中心 / 车站周边 |
| 季节风险 | 雨季、台风、严寒、高温、高原、雾季 |
| 票务制度 | 免费预约制 / 联票 / 现场买 / 需实名 |

命中类型后打开 `references/city-profiles.md`，叠加该类型的「必查项 + 常见坑 + 节奏 + 适老化调整」四项。画像结论压成一句话写进文档封面（例：「海滨 + 步行圈 + 高崎机场 25 分钟 + 台风尾季」），后面所有取舍都引用它。

## 二、硬约束（默认值，用户可覆盖）

### 2.1 适老化模式（65 岁±，自动开启）

- **硬性午休 ≥90 分钟**，写进时间表 13:00–15:00，任何景点不得挤占
- **单日 ≤2 个主项目**；第三个只能是"顺路、零成本、随时可撤"
- **不排**：爬山与长台阶、夜场演出（散场 >21:00）、单程 >2.5h 的当天往返
- **水上项目选"坐着完成"的**（竹筏/游船），不选需要划、需要平衡的
- **年龄限制单独核**：竹筏类多数 **70 岁以上禁乘**（65 岁可乘，别自己加码劝退）；免票年龄 60/65/70 各景区不一，一律带身份证原件
- 每天至少 2 个「随时可坐」锚点（观景台/咖啡馆/公园长椅）
- **早班机（≤10:30）**：前一晚收完行李 + 双闹钟 + 接驳票提前买 + 06:45 前退房

### 2.2 节奏与交通

- 一天两景 + 硬性午休；**同一天不重复同类项目**（两个筏、两座古镇、两条商业街都算重复）
- 不租车为默认；打车按「2 人分摊」算人均，写明是否含高速
- 景区内部禁行私家车 / 叫不到网约车的，必须查清接驳方式、票价、运营时间、末班
- 折返路线不藏：机场→市区→目的地这种"为某个点绕路"的结构，明写多花多少 km / 小时
- 住宿选址三选一（景区步行圈 / 枢纽周边 / 商业中心），老人同行优先**景区步行圈**；早班机优先枢纽

### 2.3 表达

- 不写"建议提前预约、注意防晒、带好证件"这类零信息量句子
- 正确写法：「UV 6.6，10:00–15:00 遮阳帽 + SPF50」「公众号每晚 20:00 放次日票，10.16 晚准点抢」

## 三、流水线（Step 0–6）

**Step 0 画像**：按 1.1 定类型，加载对应必查项（`references/city-profiles.md`）。这一步决定后面查什么，不能跳。

**Step 1 锚定**：把不可变项排成时间轴 —— 航班/高铁 → 落地接驳 → 酒店入住 → 每日首末项目 → 返程接驳 → 起飞。锚点之间才填玩法。

**Step 2 核验**：按第四节通用清单 + 该城市类型的专属清单逐项查，每条记「数值 + 来源 + 抓取日期」。查不到就写"未核实"，不拍脑袋。

**Step 3 排日程**：锚点倒推。每天 = 上午 1 主项目 + 午餐 + 硬午休 + 下午 1 主项目 + 晚餐。每段标车程（km / 分钟 / 价格）。

**Step 4 算账取舍**：对每个"想加的点"跑第五节四笔账。不划算就明说不划算，并写清代价。

**Step 5 出文档**：按 `references/doc-skeleton.md` 的 12 章骨架生成 DOCX。改已有文档走 `references/docx-xml-playbook.md`。

**Step 6 交付**：`present_files` 出文件 + 正文一句话点出「落地前必须办的 1 件事」（通常是放票/预约的准确时间点）。

## 四、核验清单（每项都要有数值、来源、日期）

| 类别 | 必须核到的字段 | 常见坑 |
|---|---|---|
| 机票/高铁 | 班次、起降时刻、值机截载、行李额 | 早班机接驳没排，等于白买 |
| 接驳 | 首末班、发车间隔、票价、上车点、购票小程序、客服电话 | 只查"有机场巴士"，不查几点发车 |
| 门票 | 是否免费、预约渠道、免票年龄、开放时间、停止入园时间 | 免票也要预约 / 要刷身份证 |
| 水上·高风险 | 年龄身高健康限制、末班时间、**放票时间与渠道**、停运条件、退票规则 | 末班 16:30 却排 16:10 到 |
| 包车/打车 | 单程价、往返价、含不含高速、夜间加价 | 用户实测价比资料低时，以实测为准并回写"更正一处" |
| 餐饮 | 人均、招牌菜单价、称重/换活鱼/景区溢价坑 | 核心步行街价 = 巷内两倍 |
| 天气 | 最高/最低温、降水概率与量、日落、UV、体感、**多源交叉、拉取日期** | 拿"月平均气候"当三天预报 |
| 住宿 | 到核心街区步行分钟、电梯、行李寄存、早退房能否吃早、能否代叫车/代订票 | 定了"近核心区"，实际 1.5km |
| **类型专属** | 海滨：渡轮末班/台风停航/潮汐；山水：索道末班与排队；古城：联票与石板路；都市：**周一闭馆**；高原：海拔与氧气；冰雪：日照时长；境外：签证/支付/插头 | 逐条见 `references/city-profiles.md` |

天气至少交叉 3 源：中国天气网（景区页 + 市区页）、中央气象台、墨迹/彩云等商业气象站。结论取交集，分歧写区间。

## 五、四笔账（判断"要不要加这个点"的唯一标准）

```
距离账：单程 X km × 2 = 总里程 → 换算总耗时（含等车、换乘、步行）
时间账：占用当天可玩时段的百分比（>40% 要警惕，>60% 基本否决）
钱账  ：人均增量 ¥（门票 + 车费 + 可能加项 + 排队时间的机会成本）
体力账：对长辈的负荷（单程 >2h 必须拆两段；>3h 直接否）
```

固定输出句式：

> 「A → B 的交换 = 多 X km、多 Y 小时、多 ¥Z、体力 +N。值不值只取决于【唯一变量】。若【条件成立】就去；否则砍。」

并且**必须写代价**：砍掉之后会失去什么（示例：砍兴坪 = 看不到九马画山与 20 元背景）。只写收益不写代价的方案，是耍流氓。

## 六、文档骨架

见 `references/doc-skeleton.md`。核心是 12 章：封面核心信息 → 出发前必办 N 件事 → 行程总览（含天气列）→ 本版改了什么 → 天气与应对 → 逐日行程 → 必打卡 + 不推荐 → 美食 + 避坑 → 住宿 → 行李穿衣 → 预算 + 预算说明 → 应急兜底 → 落选方案留档 → 数据说明。

四条硬规则：

1. **每张表都有明确表头**，不用散文承载行程
2. **「本版改了什么」编号列条目**，① ② ③ 一路排下去
3. **数据说明放最后**，逐条标来源（官网/携程/小程序/用户实测）
4. **封面先写目的地画像结论**（类型 + 核心住宿区 + 枢纽 + 季节风险），后面每个取舍都能回指它

## 七、版本规则

- 每次用户决策 → 出新文件：`<目的地><N>天<N-1>晚（日期）·v<N><语义>.docx`，语义写清楚（`v3无兴坪骑行版`、`v4儿子载老妈版`、`v5天气更新·定不去龙脊版`）
- **不覆盖旧版**。用户可能需要回滚对比
- 已取消的项目**不删干净**：留一行「已取消 · 留档说明」，写 3 条砍的理由 + 1 条代价 + 1 条"若改主意怎么补"
- 已决事项**不重复劝**。用户说"不去龙脊"，就压成一段留档，不再每版追问

## 八、反模式

| ❌ 不要 | ✅ 要 |
|---|---|
| "注意防晒、提前订票、带好证件" | "UV 6.6；公众号 20:00 放次日票；身份证原件刷证入园" |
| 把折返包装成"顺路" | "多 33km / 多 3.5 小时，这 3.5 小时就是你为城徽付的价" |
| 用户坚持就改口说"其实也不错" | 四笔账摆出来；用户拍板后照做，并在文档里记录代价 |
| 一天塞三个点 | 两个主项目 + 硬午休 + 一个顺路零成本 |
| 价格拍脑袋 | 多源交叉；用户实测优先；不一致就写"更正一处" |
| 用"平均气候"当预报 | 标日期、标来源、标可信度、写分歧区间 |
| 景点清单式攻略 | 时间轴式行程 + 每段的车程/价格/退路 |
| 换城市却沿用上一份模板内容 | 新城市从空白骨架生成；复用模板先全文搜旧地名/店名清零 |
| 什么城市都用同一套必查项 | 先定类型，再叠加海滨/山水/都市/高原/冰雪/境外的专属项 |

## 九、交付前 10 条自检

1. 每天有午休？每天 ≤2 个主项目？
2. 每个价格有来源？天气标了拉取日期？
3. 有「出发前必办的 N 件事」？含准确放票/预约时间点？
4. 返程日有「误机/误车风险」段落（含备选方案与价格）？
5. 预算只算落地待付？给了随身现金建议？
6. 砍掉的项目留档了（原因 + 代价）？
7. 「本版改了什么」更新了？
8. 长辈的年龄限制、免票规则逐项核过了？
9. 城市类型专属项命中？（闭馆日 / 末班 / 停航 / 海拔 / 日照 / 签证）
10. 旧城市痕迹清零？（地名、店名、特色菜、上一趟的价格与链接）

## 十、技术附录

改 DOCX 用 `references/docx-xml-playbook.md`（直改 `word/document.xml`）。要点：按 `<w:tbl>` 顺序定位表格、行号 1 基、正则 `<w:t(?:\s[^>]*)?>`、跨 run 替换、删除前先看文本级上下文。
