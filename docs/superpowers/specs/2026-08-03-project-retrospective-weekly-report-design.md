# 项目复盘型成长周报设计

## 目标

把成长周报从“本周做了什么”的事项清单，升级为能够体现产品判断、创意解法、验证能力和长期沉淀的项目复盘，同时继续满足公开安全、事实可核验和低 token 消耗三项约束。

周报面向个人网站读者，不写内部工作流水账。读者应在三分钟内看懂：本周最重要的突破是什么、为什么难、采用了什么不同于常规做法的解法、结果如何被验证、这件事沉淀了什么长期能力。

## 内容结构

每周只选一个重点项目，其他已完成成果作为短复盘。

1. **本周核心判断**：100～150 字，概括本周最值得记录的能力突破，不复述项目标题。
2. **重点项目深复盘**：500～800 字，固定包含背景与难点、核心创意、关键实现、验证结果、长期价值五部分。
3. **其他成果短复盘**：2～4 项，每项 180～300 字，至少包含亮点、结果和价值，不要求重复完整五段结构。
4. **方法论沉淀**：从本周成果中提炼 2～3 条可迁移原则，每条必须能被下一个项目复用。
5. **仍然保留的边界**：列出进行中、未验证或不适合公开的内容类型，不披露项目细节。

若本周没有同时满足“已完成、可验证、可公开”的重点项目，则不强行生成深复盘；周报停止发布并报告素材不足。

## 重点项目选择

重点项目按以下顺序评分，选择得分最高的一项：

1. 是否形成了真实可查看的交付物。
2. 是否解决了一个明确而非表面的难点。
3. 是否包含可解释的产品判断或非默认解法。
4. 是否经过测试、回读、线上验证或用户确认。
5. 是否能沉淀为跨项目可复用的方法。

任务仍处于进行中时，即使已经创建部分文件，也不能成为重点项目。多个任务属于同一交付链路时合并为一个项目，避免重复计算成果。

## 公开数据契约

新增 `mrcharm-weekly-public-v2`，生成器继续兼容已有 v1。v2 只允许以下公开字段：

```json
{
  "schema": "mrcharm-weekly-public-v2",
  "weekEnding": "2026-08-07",
  "weekSummary": "本周核心判断",
  "methods": ["可复用原则一", "可复用原则二"],
  "items": [
    {
      "id": "codex-20260807-01",
      "date": "2026-08-07",
      "title": "成果标题",
      "phaseTitle": "项目或成长主题",
      "role": "featured",
      "challenge": "背景与真正难点",
      "creativeIdea": "核心创意与关键取舍",
      "execution": "关键实现动作",
      "validation": "已经发生的验证结果",
      "value": "长期价值与能力沉淀"
    }
  ]
}
```

`role` 只允许 `featured` 或 `supporting`，且必须恰好有一个 `featured`。`methods` 只能由入选成果归纳，不能生成脱离事实的通用口号。

禁止出现原始对话、提示词、代码正文、密钥、个人隐私、公司或客户内部信息、本地绝对路径，以及 `evidence`、`review`、`checks`。不确定是否适合公开时直接排除。

## 低 token 收集策略

1. 单次列出最近 50 个任务，先依靠标题、项目、状态和列表摘要过滤本周任务。
2. 只对最多 6 个“已完成且可能入选”的任务读取最近 2 个回合；不包含工具输出，每项最多保留 2500 字符。
3. 先选重点项目，再为重点项目补齐五段信息；其他任务只生成短复盘。
4. 最终最多发布 5 个项目，全文目标为 1500～2500 个汉字。
5. 缺少创意或验证事实时明确省略，不用套话补足篇幅。

## 页面生成规则

生成器按以下顺序渲染：

1. 标题与本周核心判断。
2. `featured` 项目的五段深复盘。
3. `supporting` 项目的短复盘。
4. 方法论沉淀。
5. 固定公开边界声明。

重点项目使用清晰的小标题，不把五部分压成一个长段落。短复盘允许合并“关键实现”和“验证结果”，但必须保留具体亮点。页面继续使用现有文章模板，不新增复杂视觉组件。

## 自动发布流程

`automation-4` 保持每周五 18:30 单次运行：

1. 按低 token 策略收集本周所有项目任务。
2. 生成唯一的 v2 公开 JSON。
3. 校验恰好一个重点项目、字段白名单、字数范围和隐私禁区。
4. 检查仓库为 `main`、工作区干净并完成 `git pull --ff-only`。
5. 运行现有周报脚本、测试、提交和推送。
6. 等待 GitHub Pages，并验证页面状态码和重点项目关键内容。

任一闸门失败即停止；不强推、不重置、不清理用户改动，也不退回到编造或填充式周报。

## 测试与验收

- v1 公开 JSON 继续可以生成原格式周报。
- v2 缺少重点项目、存在多个重点项目、包含未知字段或私密字段时必须失败。
- v2 页面包含核心判断、五段重点复盘、其他成果、方法论和边界声明。
- 进行中任务、模拟结果和未验证结论不会进入示例周报。
- 预览全文在 1500～2500 个汉字范围内，且不依赖重复套话达到字数。
- 自动化实际使用任务列表上限 50，并把补读任务限制为 6 个。
- 仓库状态、脚本失败和部署验证继续遵守原有安全停止规则。
